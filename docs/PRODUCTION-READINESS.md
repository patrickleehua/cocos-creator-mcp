# Windows 3.7.x 生产验收

当前状态：**正在验收，尚未标记生产稳定**。目标是 Windows x64 的官方 Creator 3.7.0、3.7.1、3.7.2、3.7.3、3.7.4 同等执行现有功能的检查。新增高级 Prefab 功能需要单独实现和验收，不用扩大工具数量代替稳定性工作。

**2026 年 10 月 18 日范围调整：八小时长测仅要求 3.7.3 和 3.7.4。** 当前五版本的功能、故障、构建和恢复检查继续完成。两版长测使用新的独立专用工程、用户配置及调试端口，与原测试隔离；总共最多两台自有编辑器，根据资源先启动一路，资源位可用后自动启动另一路。原调度器完成正在执行的功能和恢复阶段后，在下一阶段只读启动检查处交接，保留原报告及源码身份；不重复执行原调度器计划中的五版长测。3.7.0、3.7.1、3.7.2 保留实际已完成的覆盖范围，不能标为八小时通过。

首次公开提交的结果见 [STABILITY.md](STABILITY.md)。后续每个结果必须匹配新的源码哈希。已有 3.7.3 本机补丁版结果不替代官方 3.7.3；官方 Windows ZIP 已另行取得并校验，安装包和实现代码不随仓库分发。

当前源码的本地单元 / 契约检查为 **444 通过、0 失败、0 跳过**，包含场景切换返回值的两项回归。[当前修复与报告](../analysis/validation/scene-open-2026-10-17/manifest.json)保留了修改前两项失败、修改后通过及源码哈希。此前提交 `3bc71a2` 的 442 项检查和 [7 项 CI](https://github.com/patrickleehua/cocos-creator-mcp/actions/runs/38956381004)属于[历史加固快照](../analysis/validation/hardening-2026-10-17/manifest.json)，不代替本次修复后的全版本验收。

浏览器探针也需要单独验证。早期探针在页面初始化期间主动 `System.import("cc")`，产生了引擎依赖加载错误；同一编辑器、同一场景的对照复测确认，改为读取已加载的引擎后连续两次通过，旧导入探针则再次失败。现在只读取全局 `cc` 或现有 SystemJS 注册表，并检查默认 frame 上下文；引擎版本、场景 UUID、中文 Label、Canvas、渲染帧和零 JavaScript 错误的门槛保持不变。[失败与对照记录](../analysis/validation/preview-probe-2026-10-17/manifest.json)保留了两种探针的哈希。此修复属于验收工具，MCP 运行代码未改动，完整五版本验收仍需完成。

后续第 10 轮中，官方 3.7.1 完成核心、引用、extras、真实故障、100 轮、预览，以及 Web 调试 / 发布完整构建和独立浏览器检查；该轮随后在 3.7.3 的故障观察请求出现 `UND_ERR_HEADERS_TIMEOUT`，整轮保留为失败，尚未进入八小时长测。观察工具已改为只发送一次 HTTP 请求并明确控制总时限，通过本地延迟响应和错误处理检查；400 节点、1.2 秒故意超时、200 毫秒排队过期、读回和保存门槛保持不变。新一轮原生验收需重新完成，不能由观察工具检查推导原生通过。[该轮报告与观察工具检查](../analysis/validation/observer-transport-2026-10-17/manifest.json)分别保留。旧故障报告没有明确的清理确认，退出后的已保存场景未发现测试节点，也不能据此证明当时的内存状态。

第 11 轮五个官方版本均完成了上述功能、故障、100 轮、预览和两种 Web 构建检查；3.7.0、3.7.2、3.7.3 完成强制退出恢复，随后在 3.7.4 启动准备阶段读到空场景，整轮失败，未开始八小时长测。调查确认 `scene.open` 会在身份验证后另查一次场景并直接返回，因此可能把加载切换期间的空场景当作成功结果返回。现在只返回同一次验证通过的快照，要求就绪、唯一匹配的场景根节点和布尔 dirty 状态；只轮询读取，不重发打开请求。验收控制器也改为每个实际编辑器进程重新配置后台运行环境，并清理启动阶段失败的自有进程。第 11 轮全部报告与旧源码身份保持独立，修复后的五版本门槛重新执行，不能沿用旧通过结果。

修复后的第 12 轮再次完成五版本功能、故障、100 轮、预览及调试 / 发布 Web 构建，但在 3.7.4 的下一次编辑器启动中止步；同时间的原生崩溃转储记录访问异常，根因仍未知。后续独立启动检查和保存场景后的强制退出恢复均通过，场景文件摘要一致、原客户端重连、会话更新且清理完成；这些诊断不把失败轮次改为通过。[调查与报告](../analysis/validation/startup-recovery-2026-10-18/manifest.json)保留源码身份和证据边界。

第 13 轮于 **2026 年 10 月 18 日 01:01（UTC+8）失败停止**：3.7.0、3.7.1、3.7.2、3.7.4 完成功能、故障、100 轮、预览和两种 Web 构建，3.7.3 在启动就绪前退出。该次转储记录 `0x80000003` 原生断点异常，与此前 3.7.4 的 `0xc0000005` 访问异常不同，尚不能认定共同根因。该轮未进入恢复或八小时长测，失败报告及受测源码保持原样。

第 14 轮于 **2026 年 10 月 18 日 11:03（UTC+8）启动**，控制器及后续工程路径检查采用上述启动门槛，再执行有效场景 UUID、功能与恢复要求。原定五版长测现按上述范围调整为独立的 3.7.3 / 3.7.4 两版长测。保留不同调度阶段的报告与方法身份，运行源码必须一致，最终仍须审阅报告及工程路径检查才能发布稳定性结论。**目前没有任何版本完成八小时长测**，专项测试时长不计入长测。

## 本轮加固

- RPC 除请求数量外，还限制排队载荷、单次结果和结果缓存的字节数，见[请求预算](OPERATIONS.md#请求预算与不确定结果)。
- 截止时间已过的排队请求不再派发；已派发的原生写入仍保持串行，超时和断连不自动重试。
- 写入错误区分原生修改前的拒绝和修改后的未知结果，保留部分完成的 UUID 和诊断。
- 健康检查及真正派发前复核编辑器的工程身份；身份变化后拒绝把已有会话转向其他工程。
- 保存前检查资源数据库和当前场景资产身份，拒绝把临时场景或已删除资产交给交互式保存流程。
- 节点、Prefab 以及 UI 顶层创建省略父节点时，显式使用当前场景根节点。官方 3.7.3 的重复创建 / 删除曾在隐式父节点下返回场景中不存在的 UUID；显式根节点是本轮修复，并继续进入同版本、跨版本和长测验证。
- 提供可复现的八小时长测入口，记录运行源码、读回、保存重开、连接关闭和 Windows 进程资源采样。

这些保护不增加跨多个调用的事务，也不能锁住用户在 Creator UI 内同时进行的修改。生产自动化仍应保存 taskId、处理 `partial` / `unknown`，并避免与手动编辑、构建交叉进行。

## 自行运行长测

使用 [CONTRIBUTING.md](../CONTRIBUTING.md) 创建带标记的专用工程，在对应版本打开并启用扩展。这个脚本会修改、保存和创建资源，不接受未标记的普通工程。不要把集成测试标记添加到个人工程。

```powershell
node scripts/soak.mjs --project "D:/mcp-lab/creator-3.7.1" --report "D:/mcp-lab/reports/3.7.1-eight-hours.json"
```

默认时长 28,800 秒，轮间等待 1 秒。报告必须是工程外的新文件；拒绝覆盖已有报告。Windows 进程资源采样包括编辑器主进程及当时的子孙进程；默认进程树私有内存上限 8 GiB、句柄上限 30,000。这些是合成测试的停止预算，不是任意生产工程的容量承诺。样本有界保留，退出前核对源文件哈希以及 stdio 服务进程确实已关闭。

长测使用单调时钟计算时长，并监测运行连续性。监测出现超过一分钟的时间空档或时钟倒退时，按中断记录，避免让“休眠八小时”变成通过；恢复后需要重新进行完整长测。这个空档阈值保留了短暂停顿的容差。保持本机开机运行，不修改全局电源设置。

先执行有限循环检查环境：

```powershell
node scripts/soak.mjs --project "D:/mcp-lab/creator-3.7.1" --report "D:/mcp-lab/reports/3.7.1-pilot.json" --cycles 100 --duration-seconds 1800 --interval-ms 0
```

有限循环通过不会变成八小时通过；报告分别记录 `success`、`durationMet`、`elapsedMs` 和 `resourcePauseMs`。脚本每十轮保存重开场景并关闭、重建 SDK 连接；任何写入错误均停止该次运行，报告保留错误和 namespace，不自动重复写入。测试资源保留在专用目录中便于调查。

有外部资源调度器时，可通过 `--control-file <绝对 JSON 路径>` 提供 `{ "pauseUntil": <Unix 毫秒时间> }`。暂停最多提前五分钟，过期后自然恢复；`{ "abort": true, "reason": "..." }` 会在下一轮开始前停止并保存失败报告。不要在多个版本间复用同一个工程、编辑器配置目录或原生调试端口。

## 本机执行与证据归档

根据本机负载，原生功能、故障、完整构建和编辑器恢复采用单路；轻量长测阶段最多两个独立编辑器并行，进程优先级为 BelowNormal。编辑器逐台启动，前一台完整就绪后重新采样；只有可用内存至少 10 GiB、CPU 低于 85% 时才加开编辑器，可在资源不足时持续单路。可用内存低于 4 GiB 或 CPU 达到 95% 时暂停长测循环，暂停不计入八小时；连续低于 2 GiB 会中止测试，保留失败结果。初期双路重型验收曾观测到 3.83 GiB 可用内存和 100% CPU，该次运行已按资源策略调整记录为中断并[保留证据](../analysis/validation/resource-policy-2026-10-17.json)。此策略会延长运行时间，不修改系统电源设置或关闭其他工作应用。

运行中的机器日志、会话和报告先保留在忽略的本地工作目录。完成后只归档已脱敏的报告、源码哈希、官方版本身份和失败记录；不会提交会话 token、个人路径、编辑器实现或测试项目。修改运行代码会使该次同源码验收失效，需重新执行受影响检查。

八小时通过仍不等于“任何工程都无风险”。稳定版结论必须同时列明具体版本、现有功能、构建目标、恢复范围和已知限制；尚未完成的门槛保持未完成。
